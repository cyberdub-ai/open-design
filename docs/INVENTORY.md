## 1. Что это

**Это не самописный проект, а поддерживаемый владельцем форк стороннего OSS-продукта.** OpenDesign
(`nexu-io/open-design`) — local-first альтернатива Claude Design: локальный демон порождает
агентские CLI (claude, codex, gemini, opencode, qwen и др.), те по «скиллам» и «дизайн-системам»

(Electron), `apps/packaged`, `apps/landing-page`, `packages/contracts`, `tools/dev|pack|serve`, `e2e`.

## 3. Что сломано

### CRITICAL-1 — публичный домен отдавал интернету аутентифицированный доступ к агентскому демону

В блоке `open-design.cyberdub.su` живого `~/stack/n8n/Caddyfile` (строка ~1541) Caddy **сам
подставлял** заголовок авторизации за каждого анонима:

```
header_up Authorization "Bearer <OD_API_TOKEN>"
```

`forward_auth`/`authentik` в блоке нет (в том же файле 11 блоков с `forward_auth` — этот не из них).

**Проверено, а не предположено.** Запрос без единого заголовка авторизации:

```
curl -sk --noproxy '*' --resolve open-design.cyberdub.su:443:127.0.0.1 \
     https://open-design.cyberdub.su/api/projects
→ 200 {"projects":[{"id":"lls-integration-ab145f9c","name":"Integration Smoke",…
```

тот же демон напрямую: `http://192.168.2.44:7457/api/projects` → **401**. Дыру создавал именно
Caddy, не демон.

Чем опасно: за эндпоинтом демон, который (а) порождает агентские CLI на **платных подписках
владельца** — `CODEX_HOME=~/.codex-od`, `CLAUDE_CONFIG_DIR=~/.claude-od` с живыми `auth.json`;
(б) умеет писать и удалять файлы через MCP-тулы, добавленные форком владельца; (в) принимает
`POST /api/runs` и `POST /api/chat` (`apps/daemon/src/routes/runs.ts:1206,3068`). Это
неаутентифицированное выполнение кода из интернета плюс расход чужих подписок.

Это тот же класс дыры, что уже закрывали **в этом же блоке** 2026-08-01 по пути `/llm-gateway/*` —
комментарий об этом стоит на восемь строк выше.

Разбор последствий перед правкой: `grep -rIl 'open-design.cyberdub.su'` по `~/stack`, `~/bin`,
`~/scripts`, `~/.claude`, `~/projects` нашёл только бэкапы самих Caddyfile и упоминания в
исследовательских `.md`. **Потребителей публичного URL нет — снятие заголовка ничего не ломает.**
После снятия владелец заходит браузером по Basic-авторизации (логин `open-design`, пароль =
`OD_API_TOKEN`) — это штатный путь демона, `apps/daemon/src/server.ts:2716`.

**Статус: ЗАКРЫТО 2026-08-28, проверено.** Файл принадлежит проекту `44-srv`, scope-fence
запретил правку из этой сессии, и задание тоже говорит «в чужие проекты не ходить» — поэтому
готовый патч, команды валидации и гейт приёмки были переданы владеющей сессии через `ab-deliver`
(id `20260828-141855-open-design-78d860cf`). Сессия `44-srv` его применила; разбор у неё —
`~/projects/44-srv/docs/caddy-open-design-auth-bypass-20260828.md`, коммиты `2705019` (`~/stack`)
и `6c51994` (44-srv). Бэкап под откат я снял до всего: `~/stack/n8n/Caddyfile.bak-20260828`.

Проверено мной после правки, а не со слов исполнителя:

```
аноним  https://open-design.cyberdub.su/api/projects → 401   (было 200)
владелец  тот же URL с Basic open-design:OD_API_TOKEN → 200   (доступ не потерян)
демон в LAN http://192.168.2.44:7457/api/projects   → 401
```

Побочно 44-srv вскрыла инфраструктурную причину, которую стоит знать: `Caddyfile` смонтирован в
контейнер **одиночным файлом**, и его inode в контейнере мёртв с 26.08 — правка файла на хосте с
`reload` в прод не попадает. Применять пришлось через `docker cp`. Следствие шире нашего проекта:
все правки Caddyfile после 26.08 11:15 UTC в проде не действуют (три чужих хунка), нужен рестарт
caddy — это уже задача 44-srv. Сканом того же класса дыры по всему Caddyfile найдено 0 других
активных подстановок креденшелов.

### HIGH-1 — `OD_API_TOKEN` открытым текстом в git-трекаемом файле

**Статус: ЗАКРЫТО 2026-09-05, проверено.**

`restart`. Новое значение живёт только в
`~/.config/systemd/user/open-design.service`; прочитать —
`grep -oP '(?<=^Environment=OD_API_TOKEN=).*' ~/.config/systemd/user/open-design.service`.
Откат: `cp -a ~/.config/systemd/user/open-design.service.bak-20260905
~/.config/systemd/user/open-design.service && systemctl --user daemon-reload && systemctl --user
restart open-design` — бэкап хранит прежнее значение и не удаляется.

Проверено так (все шесть проб, 2026-09-05):


## 7. Интерфейс

Интерфейс у проекта есть — и по формальному признаку задания раздел применим. Но дизайн-набор
Antigravity я **не собирал**, и это осознанное решение, а не пропуск. Причина ниже; окончательный
выбор за оркестратором.

**Интерфейс здесь не наш.** Проверено `git log` по путям:

| Поверхность | Что это | Коммитов владельца |
|---|---|---|
| `apps/landing-page` | публичный маркетинговый сайт продукта, Astro + Cloudflare Workers | **0** |
| `apps/web` | само приложение, Next.js 16 + React 18 | **2**, и один из них — мердж апстрима v0.20.2 |

Топ-авторы лендинга — `xne998808-ai` (69), `lefarcen` (54), `Jane` (33): это команда `nexu-io`,
пишущая свой продукт. Владелец лендинг не деплоит и не показывает никому — он крутится у вендора
на своём домене. «Платящего покупателя до оплаты» у этой страницы в портфеле владельца нет вовсе:
open-design — не продукт на продажу, а локальный инструмент.

**Чем плох редизайн апстримового UI.** Задание Antigravity исходит из посылки «дизайн наш и он
уровня AI-slop». Здесь посылка не выполняется: переоформление чужих 3382 коммитов создаёт

накладывать заново коммитами `b93beada7` и `e733c1118`. Это при 13 точечных коммитах в демоне.
Полный ре-скин веб-UI сделает такую потерю правилом, а каждый апстрим-мерж — ручной работой.

**Что предлагаю вместо** (решение оркестратора/владельца, сам не делаю):

1. **Ничего не делать по этому проекту** — рекомендуемое. Дизайн open-design поддерживает вендор,
   он же его и улучшает; наш выигрыш от ре-скина нулевой, а цена — вечные конфликты мержа.
2. Если облик всё же не устраивает — правильный канал не форк, а **тема/дизайн-система внутри
   штатного механизма продукта**: у него для этого есть `design-systems/` (brand `DESIGN.md`) и
   `craft/`. Это расширяемая точка апстрима, она мержи переживает. Набор Antigravity тогда
   собирается не на «страницу целиком», а на одну дизайн-систему — и это другое задание.

Slug набора поэтому не заводился.
